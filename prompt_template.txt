====================
EVIDENCE PRIORITY
====================
Use what exists; higher is more trustworthy:
1) Code evidence: code.touched_files, code.base_files_at_base.path, code.commits[].patch, code.compare_diff
2) PR text + labels: pull_request.title, pull_request.body, pull_request.labels[].name
3) Repo metadata: repo.description, repo.language, repo.homepage, repo.full_name
4) Discussion/CI metadata: events (comments/reviews/check runs/statuses), code.status/context/reason

====================
SCORING RULES
====================
DOMAIN (single-label):
- For EACH domain, award 1 point for each satisfied rubric bullet.
- Choose the domain with highest score.
- If highest score < 3, DOMAIN = NONE.
- Tie-break: prefer domain supported by (1) code evidence; then (2) PR text/labels; else DOMAIN = NONE.
- If DATABASE_SQL_ORM and DATA_ENGINEERING_ETL tie: pick DATABASE_SQL_ORM when evidence is about schema/migrations/queries; pick DATA_ENGINEERING_ETL when evidence is about batch pipelines/datasets/resharding/analytics.
- If DEVOPS_NETWORK_SERVICES and BACKEND_API_SERVICES tie: pick DEVOPS when infra/deploy/runtime config dominates; pick BACKEND when app endpoints/middleware/request handlers dominate.
- If TEXT_REGEX_EDITING and WEB_FRONTEND_UI tie: pick WEB_FRONTEND_UI when UI components/CSS/browser behavior dominates; pick TEXT_REGEX_EDITING when it is primarily formatting/regex/text transformation tooling.

ATTRIBUTES (multi-label):
- Score each attribute separately with its rubric bullets (1 point each).
- Add an attribute if score >= 2 OR if there is a single very high-confidence cue (e.g., DOCS_ONLY clearly true; GENERATED_ONLY clearly true).
- If no attributes meet threshold, output an empty list [].
- Consistency guards:
  * If DOCS_ONLY is selected, do NOT select FEATURE_ADD/BUGFIX/REFACTOR_ONLY/STYLE_ONLY/API_SURFACE_CHANGE (unless the doc explicitly defines a public contract like OpenAPI; otherwise keep DOCS_ONLY alone).
  * If VERSION_BUMP_ONLY is selected, do NOT select FEATURE_ADD/BUGFIX/REFACTOR_ONLY/STYLE_ONLY (unless clear evidence contradicts “only bump”).
  * STYLE_ONLY and REFACTOR_ONLY should not co-occur with FEATURE_ADD or BUGFIX unless the PR text explicitly claims behavior change (then drop STYLE_ONLY/REFACTOR_ONLY).
  * GENERATED_ONLY should usually not co-occur with FEATURE_ADD/BUGFIX unless human-written source changes are clearly present too.

COMPLEXITY (single-label):
- Score each complexity type; choose highest.
- If highest complexity score < 2, COMPLEXITY = NONE.
- Tie-break: prefer LOGIC_HEAVY over KNOWLEDGE_HEAVY over OBSERVATION_HEAVY unless the PR is explicitly about a subtle/rare edge case (then OBSERVATION_HEAVY can win).

====================
DOMAIN RUBRICS (1 point per bullet)
====================

SECURITY_FORENSICS:
- PR is about security hardening or vulnerability remediation (auth, permissions, input validation, secrets, crypto, safe parsing/execution).
- Changes touch security-sensitive areas (auth/authz flows, validation/sanitization, secret handling, encryption/keys, security headers).
- PR text/labels explicitly mention security (security fix, vulnerability, CVE/CWE, exploit, XSS/CSRF/SSRF, leak, hardening).
- Diff removes/mitigates risky behavior (tightens checks, adds validation, prevents injection/execution, reduces secret exposure).
- Repo context indicates security tooling or security-critical components.

DEVOPS_NETWORK_SERVICES:
- PR is about deploying/operating/monitoring services (CI/CD, infra, containers, orchestration, reverse proxy, certs/TLS, logging/metrics infra, rate limiting at infra layer).
- Changes modify infrastructure or deployment/build configuration (pipelines, container files, k8s/helm/terraform/ansible, webserver configs, system services).
- PR text/labels emphasize ops concerns (deploy, release, reliability, scaling, ports/routing, TLS, observability plumbing).
- Diff changes runtime configuration/limits/timeouts/resources rather than app features.
- Repo context is infra/platform/service management.

DATA_ENGINEERING_ETL:
- PR is about ingesting/transforming/moving data at scale (ETL/ELT, pipelines, schema mapping, partitioning/sharding, batch jobs, analytics outputs).
- Changes are in pipeline/job/workflow code (DAGs/jobs/transforms/connectors) or dataset layout/serialization.
- PR text emphasizes data correctness, schema evolution, backfills, aggregation, data quality, pipeline performance.
- Diff shows dataset manipulation (merges/dedupes/reshards/partitioning/file layout/format conversions).
- Repo context is analytics/data platform/datasets.

ML_DEEP_LEARNING:

- Changes touch model architecture/config, training/eval scripts, inference endpoints, checkpoints/weights.
- PR text mentions ML metrics/concepts (loss/accuracy/embedding/fine-tune/inference latency/model selection).
- Diff shows ML framework usage or model-serving patterns.
- Repo context is ML-focused.

SYSTEMS_EMULATION_VIRTUALIZATION:

====================
ATTRIBUTE RUBRICS (score each independently; 1 point per bullet)
====================

TESTS_INCLUDED:
- Adds/updates test files (test/ specs, *test* naming) or assertions that validate behavior.
- PR text says tests were added/updated or describes how to test.
- Diff includes new test cases, fixtures used by tests, or new assertions for the change.

REPO_ENV_SETUP_IN_REPO:
- Repo contains setup instructions or environment definitions (CONTRIBUTING, README setup, Dockerfile, compose, env files, CI configs, dependency files).
- Evidence from repo file lists or base files indicates reproducible setup (lockfiles, build scripts, containerization, CI pipeline).
- PR touches or references these setup files, implying setup is discoverable in-repo.

METRIC_IMPROVEMENT_CLAIMED:
- PR text claims measurable improvement (speed/latency/memory/throughput/accuracy/benchmark score).
- PR text includes before/after numbers, percent changes, or benchmark names.
- Diff includes performance-focused changes with explicit metric discussion in text/reviews.

DOCS_ONLY (high-confidence single cue allowed):
- All touched files are documentation or prose (docs/, README, *.md/*.rst) and no code files are changed.
- Diff contains only documentation changes (no executable logic).

VERSION_BUMP_ONLY (high-confidence single cue allowed when obvious):
- Nearly all touched files are dependency manifests/lockfiles/version pins/release metadata, with no meaningful source-code changes.
- Diff is dominated by version changes, resolved dependency graphs, or checksums/lockfile churn.
- PR title/body/labels indicate dependency/version bump automation.

API_SURFACE_CHANGE:
- Changes public-facing API endpoints/contracts, exported interfaces, SDK surface, CLI flags, or externally consumed schemas.
- PR text mentions breaking changes, new/changed endpoints, contract updates, or deprecations.
- Diff updates interface definitions, public methods, route schemas, OpenAPI/GraphQL specs, or wire formats.

OBSERVABILITY_CHANGE:
- Adds/changes logging, metrics, tracing, instrumentation, dashboards, alerting hooks.
- PR text mentions logs/metrics/traces/monitoring/observability.
- Diff adds instrumentation calls, log fields, metric counters, tracing spans, or config for telemetry.

SECURITY_FIX:
- PR explicitly addresses a vulnerability or hardens auth/permissions/validation (including dependency update explicitly for a security advisory).
- PR labels/text mention security/CVE/CWE/exploit/hardening.
- Diff reduces attack surface (validation, sanitization, auth checks, secret handling).

STYLE_ONLY (high-confidence single cue allowed when obvious):
- Diff is formatting/whitespace/comment/import-order only with no behavioral changes.
- PR text says “format”, “lint”, “style”, “prettier/formatter”, “no functional changes”.

REFACTOR_ONLY:
- PR restructures code without intended behavior change (renames/moves, reorganizes modules, simplifies structure).
- PR text says “refactor”, “cleanup”, “no behavior change”.
- Diff mostly reorganizes code paths while preserving logic.

FEATURE_ADD:
- Adds a new user-visible capability, endpoint, UI behavior, supported platform, or new workflow.
- PR text says “add”, “introduce”, “support”, “implement new”.
- Diff includes new code paths/modules enabling new behavior.

BUGFIX:
- Fixes incorrect behavior, edge cases, crashes, wrong outputs, or regressions.
- PR text says “fix”, “bug”, “regression”, “incorrect”.
- Diff changes logic to correct behavior, often with a test.

GENERATED_ONLY (high-confidence single cue allowed when obvious):
- Only generated artifacts changed (generated clients/bindings, compiled outputs, snapshots, vendored generated code).
- Paths or file headers indicate generated output; changes look machine-produced (large uniform diffs).
- No hand-written source changes are present.

====================
COMPLEXITY RUBRICS (1 point per bullet; choose best or NONE)
====================

KNOWLEDGE_HEAVY:
- Requires familiarity with established frameworks/platform conventions to implement correctly.
- PR relies on correct usage of specific APIs/patterns (framework config, ORM semantics, auth flows, UI frameworks, GPU toolchains).
- Evidence suggests “knowing the right tool/pattern” is central (comments/reviews mention best practices, framework idioms).

LOGIC_HEAVY:
- Requires careful multi-step reasoning/state management (concurrency, distributed interactions, complex control flow).
- Changes span multiple interacting files/modules where correctness depends on coordination.
- Diff introduces nontrivial algorithms, synchronization, protocol/state-machine-like logic.

OBSERVATION_HEAVY:
- Fix hinges on a key insight/subtle edge case (race condition, rare bug, tricky condition).
- PR text/reviews mention subtlety, rare reproduction, flakiness, tricky root cause.
- Small change with large behavioral impact suggests insight-driven fix.
